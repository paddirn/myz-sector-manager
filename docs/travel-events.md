# Automatic Zone Travel Events

For current opt-in tracing and read-only setup checks, see the
[0.1.62 diagnosis guide](travel-event-diagnosis.md). The 0.1.62 update explicitly adds blank-sector checks; saved-Normal probabilities
and the other game rules below are retained. Earlier saved-Normal-only eligibility
text describes the previous behavior.

## Set up in a backup world

1. Configure the existing Zone Map/Tracking integration and designate the Party/Expedition Scene tokens. Automatic checks use these exact assignments, not every token belonging to an Actor. Create and save Normal sector records for the map squares where checks should run.
2. Open **Module Settings → MYZ Sector Manager → Party Roster**. Choose an expedition assignment, then drop each participating Actor from the Actors directory or a compendium. The roster stores complete Actor UUIDs only. Portraits/names come from the referenced document; Open Actor Sheet does not copy or modify it. Set Enabled, optional Lead Stalker, and eligibility. A shared default roster is used only when exactly one expedition is registered and that expedition has no explicit members. Multiple expeditions require their own assignments.
3. Open **Document References → Travel Events → Weather Conditions** (`travelEvents.weatherTable`). Assign a world or compendium RollTable through drag-and-drop or its full UUID. Ordinary text results such as a condition name are sufficient. No weather table, world-specific UUID or proprietary content is bundled. Optional structured results may use `flags.myz-sector-manager.weather.condition` and `.description` strings; mechanical modifiers are not applied.
4. Configure the existing Threat Type and its Humanoid/Monster/D66 Encounter subtype resources in Document References. Travel encounters reuse the manual Encounters selection logic, excluding Phenomena with the existing bounded reroll. Their relative probabilities, document types and complete page-specific UUIDs are retained. Linked Journal/Page text and Actor system.description, when available, are copied into the private report as safe plain-text snapshots; original table text remains the fallback. A result may be friendly, neutral, hostile or just a discovery; no combat or enemy tokens are created. Travel checks do not require Environment/Ruins/Artifacts tables and do not append entries to sector collections.
5. Open **Travel Events** to review probabilities, enablement, Stalker mode, reporting and retention; use **Save Configuration**. Configuration is world-scoped and GM-editable. Changes and Cancel use the same draft/unsaved-change approach as the other module settings.

## Defaults and probabilities

Automatic events and Normal Sector entry are enabled. Weather changes and ordinary encounters each use an independent **1 in 12** check. Explored/Cleared sectors use **1 in 20** encounters when reduction is enabled. Unexplored, Scouted, Visited and Lost use the standard chance; no separate exploration flag is added. Turning reduction off restores the standard chance everywhere. Weather probability never depends on exploration.

All probabilities are configurable integer denominators from 1 through 1,000,000. Presets include 6, 12, 20 and 36. A denominator of 36 rolls a uniform **1d36**, never a d66 interpreted as 1–36. Invalid settings are rejected by the settings form and runtime validation. Find the Path, all eligible Stalkers, GM reports and meaningful-event history are enabled by default. Delivered history retention defaults to 200.

## Weather behavior

Weather is global to the configured Zone and shared by every expedition. The first eligible check establishes it from the configured Weather Conditions table, without a weather-only popup. Later checks roll the weather-change chance; only a different condition changes the state and creates a report. Comparison ignores capitalization and repeated whitespace; identical conditions retain the existing state/timestamp. Condition, description, source table UUID, previous condition and last-change timestamp are retained privately across reloads.

Travel Events displays the current condition without rolling. **Refresh Weather / History** rereads saved state. **Set Current Weather**, **Reroll Current Weather** and confirmed **Reset Current Weather** are explicit immediate actions, independent of Save Configuration. Reset makes the next eligible check establish initial weather silently again. No weather mechanics or Actor effects are applied. A missing/disabled/invalid weather table is diagnosed, skips weather generation and does not block encounter checks or create an error-only travel popup.

## Verified MYZ skill adapter and privacy

No licensed Foundry installation is available in the cloud. The adapter was verified against the public official system **14.0.4**, commit [`ade55c93a4c6c29828dee790aaeed4fbd81803b9`](https://github.com/superseva/mutant-year-zero/tree/ade55c93a4c6c29828dee790aaeed4fbd81803b9):

- [Skill data model and prepared totals](https://github.com/superseva/mutant-year-zero/blob/ade55c93a4c6c29828dee790aaeed4fbd81803b9/module/data-model.js): embedded skill Items use `system.skillKey === "FINDTHEPATH"`, `system.value` and `system.attribute`. Prepared `attributeDiceTotals` and `skillDiceTotals` include current attribute, skill and gear modifiers.
- [Native skill rolling](https://github.com/superseva/mutant-year-zero/blob/ade55c93a4c6c29828dee790aaeed4fbd81803b9/module/item/item.js): reads those pools through `actor.getRollData()`.
- [Public dice helpers](https://github.com/superseva/mutant-year-zero/blob/ade55c93a4c6c29828dee790aaeed4fbd81803b9/module/component/dice-roller.js), exported by `game.myz`: `DiceRoller.ParseResults` and `CountSuccesses` provide native die interpretation, including negative Skill dice canceling successes.

Automatic eligibility requires one actual Find the Path skill with a value above zero; character names and displayed role labels are never used. The GM can Include a member with a real zero-level skill or Exclude a member; overrides do not fabricate an absent skill or unknown data schema. Select a skill explicitly if duplicate Find the Path Items make the choice ambiguous. Unsupported/missing data or inaccessible Actors leave awareness unresolved with a GM-visible explanation.

Every check resolves the Actor and current roll data again. The adapter evaluates a private `db`/`ds`/`dg` Roll and uses the public result helpers directly. It does **not** call `Item.roll`, `DiceRoller.Roll`, `SendToChat`, `toMessage`, 3D-dice broadcast or Push. No Actor values, trauma, resources or gear are updated. Negative Skill pools use the absolute number of dice and the signed pool value in native parsing. Individual dice, modifiers and net success counts are recorded only in GM reports/private state.

All eligible Stalkers roll once and the highest individual result is used. Lead mode rolls only the eligible designated lead; if unavailable, it reports that fact privately and falls back to all eligible roster Stalkers. Missing/disabled/untrained members do not receive invented checks. If nobody can be rolled, the encounter still resolves, with awareness left to the GM.

One or more successes suggest spotting signs first; no successes mean no advance warning, **not an automatic ambush**. Hostility, circumstances and any additional advantage remain the GM's decision. This awareness interpretation is a clearly labeled optional automation/house rule, not a claim about strict MYZ rules-as-written.

## Entry processing and Macro coexistence

The existing completed-movement dispatcher owns coordinate detection for Travel Events and sector Macros. It uses the existing token-center/grid math. Pending/paused v14 waypoints wait for stop; same-sector updates, pass-throughs, duplicate hooks, unrelated tokens, Special sectors, initial rendering and ordinary Scene reload do not generate entries. Unsaved initial sector records are also skipped. Legacy Normal sectors without a sectorType value remain supported.

Processing order is Travel Event check → one combined GM report if anything happened → sector Macros in their existing order. The report stays open until the GM explicitly uses Close or the window X. There is no dismissal timer. Both controls resolve its awaited Promise before subsequent Macros continue. Reports and additional sector entries are queued sequentially, so no overlapping Travel Event windows open. Token movement and normal Foundry interaction are not canceled. Additional genuine moves during a travel report queue independently; Macro-induced reentry remains suppressed during Macro execution. Run Once/repeat/disabled Macro behavior and Macro execution history are unchanged. Macros that themselves open dialogs must continue to return a Promise if subsequent Macros should wait for interaction.

Weather-only, encounter-only and combined events use one compact, scrollable, active-GM-only dialog. Initial weather, identical weather, failed probabilities and configuration errors alone never open it. No public message or player roll request is made. Open Encounter Reference uses the exact Actor/Journal/Page reference without closing the report, activating a Scene or placing tokens. Successful reports never use notification toasts. A report remains visible to its GM if active-GM authority changes; removing that user’s GM role closes the private window to prevent player access, leaving its event pending for GM review.

## Private persistence, recovery and limits

Weather, event reports, dice summaries and diagnostics live in `flags.myz-sector-manager.travelEvents` on the existing **GM-owned configuration Journal**, not a publicly readable world setting. Records include original code/name, stable sector Journal ID, expedition/token identity, timestamp, encounter and Stalker details. Sector History and Macro history are untouched. `game.myzSectorManager.travel.weather()` and `.history()` are GM-guarded; `.configure()` and `.roster()` open the two settings windows.

Delivered history keeps the configured last 200 events by default (10–1000 configurable); confirmed Clear delivered history preserves pending events, weather and all Macro/sector data. The recent processing-ID buffer is 1000; diagnostics keep 50 entries. Failed chance checks never fill visible event history. Pending reports are retained for later GM review, including when normal history recording is off; successful review acknowledges them without deleting the event. Displayed reports remain in history after Close/X even when the optional recording of events with dialogs off is disabled. At 1000 pending reports new checks stop with a diagnostic instead of silently dropping generated events. Review events before continuing.

A processing marker is saved before rolling. A crash during an incomplete check is shown in Diagnostics and does not automatically reroll dice or replay side effects; the GM can use manual testing controls. If active GM authority changes during generation, the former GM can retain already obtained results in a separate, isolated `pendingTravelReports` outbox on the private Journal, subject to native GM write permissions. The next active GM merges these into pending history without rerolling. A newer weather update/reset is not overwritten. Losing GM permissions or the server connection can prevent this write; native permissions are never bypassed. Interrupted checks remain inspectable, and uncompleted portions are not claimed to have succeeded.

When **no active GM is present**, a small movement recorder can retain the originating token owner's completed raw positions in the Token's additive `pendingTravelEntries` flag. It stores no weather, encounter, skill results or sector secrets. The returning active GM validates current expedition assignments and maps these positions through the existing grid, ignoring unrelated/same-sector/Special destinations. This processes previously recorded travel, not a fresh entry merely caused by reload. Historical recovery does not execute sector Macros. Each token buffers 50 moves; overflow is counted and reported to the GM. If native Token-flag permissions deny the owner's write, the recorder logs the failure and cannot guarantee offline recovery; it never elevates permissions. Recovery uses the currently configured map/grid. No disconnected client can guarantee preserving an in-memory result that was never saved.

## Manual tests and diagnostics

The GM Testing section offers Test Weather Roll, Test Encounter Roll, Test Find the Path and Run Travel Event Check. Select a registered expedition and saved Normal sector for encounter/detection/full tests; Weather-only testing works without those selections. Tests are clearly marked TEST and use **saved** configuration. Persistence is off by default: no weather/history/processing/Macro/exploration state is written. Find the Path test results appear in the private test-results area. Enabling persistence permits test weather/history writes; Weather-only testing persists the chosen condition when requested. No test creates combatants or tokens.

Missing references are diagnosed in Document References and the Travel Events Diagnostics section. Repeated identical resource warnings are deduplicated. Actual encounters still report when detection is unavailable. Configure all required subtype tables and update nested Threat Type links if those tables change. Profile edits and configuration saves detect a stale settings baseline before writing; weather/history actions run in the travel queue. This is not a distributed database transaction.

Automated tests use simulated native APIs, real Chromium interaction and actual PIXI/WebGL rendering; they do not constitute in-game validation. In a backup Foundry v14 world, check real roster/compendium payloads, current equipped/injury modifiers and negative Skill dice, native custom dice parsing, no public/3D dice leakage, Player-originated animated paths and teleports, normal/Special transitions, two GMs and handover, offline Token permissions/recovery, pending report review, repeated visits and both Macro modes. Also verify world restart persistence, disabled options, long reports, narrow layouts and the manual dry-run controls.

## RollTable results and nesting (v0.1.26)

Use **Name** for the result label and **Description** for optional supporting text. Name-only rows are valid. Description-only legacy rows remain supported; without a Name, their description supplies the label. For stable weather identity, give each condition a short Name and put its multiline narrative in Description. Descriptions have no separate short character cap; weather labels are limited to 4000 characters. Comparisons use the label only, so changing narrative text alone does not produce a weather event.

Weather, encounters and normal sector generation use the same resolver. Each table uses its own formula/weighting through `roll({recursive:false})`; selected nested RollTables are rolled once each until a terminal result is reached. World and compendium tables work at multiple levels. The internal `MAX_TABLE_DEPTH` defaults to 10; cycles, excessive depth, inaccessible/missing targets and empty results fail with configuration/table/result context. Existing Threat Type classification and Phenomena exclusion remain in place; configure the category tables in Document References as before. Actors and Journals are terminal encounter documents, never rolled as tables.

For weather, terminal text is preferred. A linked JournalEntry or JournalEntryPage is also accepted using the row Name, or the linked document’s name when the row Name is blank, with the row Description as optional narrative. Its Journal body is not automatically used as weather identity. Actor, Item, Scene and other terminal document types produce a clear configuration error. Failed weather resolution keeps the previous weather and does not modify sector data. Encounter reports preserve row Name and Description plus linked document details when available.

The linked target is **documentUuid**. The TableResult’s own **uuid** identifies the embedded result, not the Actor/Journal/nested table. This distinction was checked against the [community v14.366 schema declarations](https://github.com/League-of-Foundry-Developers/foundry-vtt-types/blob/main/src/foundry/client/documents/table-result.d.mts), which expose Name, Description and documentUuid. The official API website was unavailable to this environment (HTTP 403). Live Foundry deprecated getters are never read; legacy plain data adapters can still supply their own data properties. Full errors/stacks remain in GM diagnostics and the console; recurring identical configuration warnings are deduplicated.

Regression checks also reproduce the prior “Illegal invocation” in real Chromium: inheriting from Window via `Object.create(window)` breaks the native `document` getter. Generation now receives an authority callback while retaining the original environment. This is browser evidence, not a claim of live Foundry testing. Before using a production world, test your actual Name-only/nested Weather and Encounter tables, both dialog close controls, queued entries, linked document opening, long descriptions, GM handover and following sector Macros in a backup v14 world.
